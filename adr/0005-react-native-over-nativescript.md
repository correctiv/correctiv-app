# ADR 0005 — React Native / Expo is the stack, NativeScript is archived

Status: accepted, 2026-08-05. Supersedes nothing; records the decision that
[ADR 0004](0004-react-native-pivot.md) began and phase 4 completed.

## Context

ADR 0004 moved the app to Expo / React Native and kept the NativeScript app beside
it while the Expo one caught up. Phase 4 is finished: all five tabs, onboarding, the
join flow and Backstage exist, 273 headless tests, and the app builds and launches
on Android.

That raises the question ADR 0004 deferred: keep both and compare in practice, or
commit to one? The pull towards NativeScript is real and worth naming, because it is
not nostalgia — it is a better *concept* in one specific way.

## What NativeScript is genuinely better at

- **Direct native access from TypeScript.** `java.lang.Object`, `UIApplication` are
  simply there. No native module to write, no config plugin to remember.
- **A view layer you can swap.** NativeScript core is framework-agnostic; Vue,
  Angular, Svelte or none.
- **A smaller substructure.** No Fabric / JSI / Hermes / New-Architecture layering
  to reason about.

## 1. Decision

**React Native / Expo is the stack.** After the device test passes, the
NativeScript app is removed from `main` and archived as the annotated tag
`nativescript-final`.

Two requirement-driven facts settle it, and neither is a matter of taste:

1. **NativeScript has no web and no Linux target** — verified, not assumed: iOS,
   Android, visionOS only. The web target is a requirement here, not an extra, and
   development happens on Linux.
2. **iOS without a Mac.** EAS builds in the cloud; NativeScript has no equivalent.

Ecosystem depth decided the third question. `@nativescript-community/audio` has no
`headers` on its source, which made the authenticated Castopod podcast *unbuildable*
(see [ADR 0003](0003-audio-capability-spike.md)); expo-audio has headers, background playback,
lock-screen controls and a web implementation.

## What we give up, explicitly

Direct native access, the swappable view layer, the smaller substructure, and
proximity to CORRECTIV's Vue house (beabee, faktenforum). The last one is the
sharpest loss and was already noted in ADR 0004.

## What we keep — and this is the part that matters

The framework independence worth having is **in `packages/app-core`**, not in the
view layer. The core is framework-free and `test/boundary.test.ts` enforces it:
`vue`, `pinia`, `react`, `react-dom`, `react-native` and `expo` are all forbidden
imports. It holds the domain — feeds, parsers, the stores, membership,
participation, podcasts, video — and would run under Svelte or Vue tomorrow. What
is React-bound is the view layer, which is the part any framework change rewrites
anyway.

NativeScript's independence, by contrast, was an option that would never have been
exercised: one framework would have been chosen (Vue) and kept, while the cost —
a thinner plugin ecosystem — was paid every day.

## Both stacks charged rent; the difference is where

NativeScript's traps were **runtime** traps with silent wrong behaviour: Vite 8
dropping the polyfills while the build stayed green (ADR 0002), `ns build` syncing
the *previous* bundle as a success, SFC `<style>` blocks extracted and never
applied, `@tap.stop` compiling to an export nativescript-vue 3 does not have.

Expo's traps were **configuration** traps: a config plugin not listed in `app.json`
so background audio was never wired, `BottomTabBar` imported from the wrong path
pulling a second React instance, typed routes generated by a different command than
the one you ran, `react` one patch release ahead of the renderer RN bakes in. All
annoying, all documented in the README table, all fixed once and gone.

Complexity you can read documentation about is cheaper than thinness you have to
build around.

## Why not keep both to compare

- **Parity is the cost.** A comparison only means something if both apps keep
  feature parity, which doubles every screen, every token change and every core
  change (a second binding plus a second set of tests).
- **The core is already not shared.** The NativeScript app carries its own audio and
  podcast stores; the core gained a podcasts store in phase 4c that the
  NativeScript app does not use. The drift happened inside one session, with nobody
  doing anything wrong.
- **One device, one app.** Both declare the package id
  `org.correctiv.app.prototype`, so they cannot be installed side by side. A
  practical comparison would need a second id — work that exists only for the
  comparison.
- **The decisive criteria are already measured**, see above.

## When to revisit

If the web target is dropped **and** a Mac is available, NativeScript + Vue becomes
defensible again — closer to the house style, direct native access, a smaller mental
model. `nativescript-final` is then a starting point, not a relic: branch from the
tag.

Until then, the tag is the fallback for exactly one scenario — the device test
finding something in the Expo build that cannot be fixed.

## Consequences

- Phase 5 removes `apps/mobile` and renames `apps/mobile-rn` → `apps/mobile`. What
  must be pulled out of the NativeScript app first is listed in ADR 0004's open
  section: the authenticated-podcast spike server and the bundled feed snapshots
  with their generators (the latter being option (b) of the open CORS question).
- The CI job named "Android debug build" builds `apps/mobile` today, so the swap
  points it at something CI has never built. The Expo app's first Android build
  happened locally on 2026-08-05 and succeeded.
- The NativeScript traps move out of the README into ADR 0004, where they are
  history rather than instructions.
